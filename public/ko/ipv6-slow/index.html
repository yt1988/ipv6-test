IPv6가 IPv4보다 느린가요?

IPv6 자체는 느리지 않습니다. 헤더가 조금 클 뿐이고, 측정할 수 있는 차이는 없습니다. 다른 것은 경로입니다. 통신사의 IPv6는 회선이 적거나 멀고, 다른 네트워크와의 IPv6 연결이 적거나, 터널을 거칠 수 있습니다. 그래서 IPv6가 더 빠른 망(NAT가 없고 설비가 새것)도 있고 확실히 느린 망도 있습니다. 위 비교에서 어느 쪽인지 알 수 있습니다.

IPv6가 느리거나 끊기는 이유는?

흔한 원인을 많은 순서대로:

  • 먼 경로: 많은 통신사가 IPv6로 해외나 다른 네트워크에 나갈 때 IPv4보다 적은 교환 지점을 거쳐 수십 밀리초가 늘어납니다. 중국 본토에서 해외로 가는 IPv6는 자주 돌아갑니다.
  • MTU 문제: 최대 크기의 IPv6 패킷이 어떤 구간(PPPoE, 터널)에서 사라져, 작은 요청은 되는데 큰 페이지가 멈춥니다. 위의 대형 패킷 테스트가 이것을 확인합니다.
  • 터널: 6to4와 Teredo의 IPv6는 멀리 있는 중계를 거칩니다.
  • 공유기: 오래된 펌웨어, 응답을 버리는 IPv6 방화벽, 자기 회선에는 IPv6가 없는데 IPv6 주소를 나눠 주는 공유기.
  • IPv4만 처리하는 프록시나 VPN이라 IPv6는 그대로 나가는 경우.

느린 IPv6는 어떻게 고치나요?

다른 시간대에 다시 측정해 보세요. 저녁에만 느리다면 통신사 쪽 혼잡입니다. 대형 패킷 테스트가 실패하면 공유기의 WAN 또는 IPv6 설정에서 MTU를 낮추세요(PPPoE라면 1480 또는 1452). 공유기와 모뎀을 업데이트하고 다시 시작하세요. IPv6가 항상 훨씬 느리다면 위 수치를 통신사에 보내세요. 경로는 통신사가 고쳐야 합니다. 그동안에도 IPv6 연결이 느리면 브라우저가 자동으로 IPv4로 바꾸므로(Happy Eyeballs) 대부분의 사이트는 그대로 됩니다.

IPv6를 꺼야 하나요?

보통은 아닙니다. 끄면 IPv6 전용 사이트와 일부 앱, 게임이 안 되고, Microsoft도 IPv6를 끈 Windows를 지원하지 않습니다. IPv6가 정말 나쁘다면 IPv4를 우선으로 하고 IPv6는 필요한 곳에 남겨 두세요. Windows에서는 레지스트리 값 DisabledComponents를 0x20으로(Microsoft의 "IPv6보다 IPv4 우선"), Linux에서는 /etc/gai.conf의 "precedence ::ffff:0:0/96 100" 줄의 주석을 해제합니다.

이 테스트는 무엇을 확인하나요?

브라우저가 일반 사이트를 여는 것과 같은 방식으로 작은 테스트 주소 몇 개를 엽니다.

IPv4 전용과 IPv6 전용 사이트: 각 인터넷에 연결되는지, 어떤 주소로 연결되는지.

듀얼 스택 사이트(둘 다 있음): 브라우저가 무엇을 고르는지, IPv6를 기다리다가 포기하지는 않는지.

IPv6 큰 패킷: 새 연결에서 최대 크기 패킷이 필요한 큰 요청을 보냅니다. 경로 MTU가 고장 나 있으면 작은 요청은 되는데 큰 요청은 사라지고, 페이지가 로딩 중인 채로 멈춥니다.

이름 없는 주소(IPv6 하나, IPv4 하나): DNS 없이 IPv6가 되는지, NAT64를 쓰는 IPv6 전용 네트워크인지.

각 테스트는 두~네 곳(Cloudflare, Google, DNSPod, AliDNS, icanhazip, ipify)에 동시에 묻고 가장 먼저 온 응답을 씁니다. 한 곳이 막히거나 느려도 실패하지 않습니다.

점수는 어떻게 계산하나요?

10점 만점이며, 네트워크가 IPv6에 얼마나 준비되어 있는지 보는 test-ipv6.com의 방식을 따랐습니다. IPv6 전용 사이트가 열리면 4점, IPv6로 큰 패킷이 통과하면 2점, 듀얼 스택 사이트가 기다림 없이 열리면 2점, DNS 없이 IPv6가 되면 1점, 브라우저가 IPv6를 고르면 1점입니다. IPv6 첫 응답이 3초를 넘으면 1점 감점. IPv6가 아예 없으면 0점이지만, 모든 사이트는 IPv4로 그대로 열립니다.

10점은 IPv6가 어디서나 되고 아무것도 느리게 만들지 않는다는 뜻입니다.

IPv6가 없습니다. 어떻게 쓰나요?

한국의 주요 통신사는 대부분 IPv6를 제공하지만, 공유기에서 꺼져 있는 경우가 많습니다. 공유기 관리 페이지에서 IPv6(또는 WAN → IPv6) 설정을 찾아 통신사 방식(보통 DHCPv6 또는 자동)으로 켜고, 내부 네트워크에 IPv6 주소를 나눠 주는 설정(SLAAC 또는 DHCPv6)도 켜세요.

공유기에 설정이 없거나 통신사가 지원하지 않으면 고객센터에 문의하세요. 휴대폰 모바일 데이터는 Wi-Fi에 없더라도 IPv6가 있는 경우가 많습니다.

IPv6가 없어도 인터넷은 문제없습니다. 모든 사이트가 IPv4로 열리고, IPv6 전용 사이트와 앱만 쓸 수 없습니다.

IPv6 주소는 되는데 IPv6 전용 사이트가 안 열려요

IPv6 연결 자체는 괜찮지만 DNS가 IPv6 주소(AAAA 레코드)를 돌려주지 않아서, 브라우저가 사이트에 IPv6 주소가 있다는 것을 모르는 상태입니다. 흔한 원인: 공유기의 AAAA 필터 설정, AAAA 레코드를 버리는 DNS 서버, DNS를 직접 처리하는 프록시.

공유기의 AAAA 필터를 끄거나 1.1.1.1, 8.8.8.8 같은 공용 DNS를 설정하세요.

큰 패킷 테스트(MTU)가 무엇인가요?

데이터는 최대 약 1,500바이트의 패킷으로 오갑니다. 일부 IPv6 경로(터널, PPPoE, 잘못 설정된 공유기)에서는 최대 크기 패킷이 어느 구간을 지나지 못하고, "더 작게 보내라"는 알림마저 막힙니다. 작은 요청은 되니 연결은 멀쩡해 보이지만, 큰 페이지나 이미지, 다운로드가 계속 멈춥니다.

테스트는 새 연결에서 IPv6 전용 호스트에 3.5KB 요청을 보내, 양방향 모두 최대 크기 패킷을 씁니다. 작은 IPv6 테스트는 통과하는데 이 항목이 실패하면, 공유기의 IPv6 또는 WAN 설정에서 MTU를 낮추거나(PPPoE는 1,480 또는 1,452) 통신사에 문의하세요.

IPv6가 되는데 브라우저는 왜 IPv4를 고르나요?

브라우저는 둘 다 시도해서 먼저 연결되는 쪽을 씁니다(Happy Eyeballs). IPv4가 이기는 것은 내 네트워크에서 IPv6 연결이 더 느리거나, 시스템이 IPv4를 우선하기 때문입니다. Windows는 터널 IPv6(6to4, Teredo)일 때 그렇게 하고, IPv4만 전달하는 프록시와 VPN 앱도 많습니다. 고장은 아니며 IPv6 전용 사이트는 열립니다.

프록시나 VPN을 쓰고 있어요. 누구의 결과인가요?

대부분 프록시의 결과입니다. 프록시를 켜면 테스트 사이트에 프록시를 거쳐 접속하므로, 보이는 주소와 IPv6 지원은 프록시 서버의 것입니다. IPv4만 전달하는 프록시라면 IPv6가 없는 것처럼 보입니다. 내 네트워크를 테스트하려면 프록시를 끄거나(또는 이 호스트들을 직접 연결로 두고) 다시 테스트하세요.

NAT64를 쓰는 IPv6 전용 네트워크란?

일부 모바일 네트워크는 휴대폰에 IPv6만 줍니다. 그래도 IPv4 전용 사이트에 접속할 수 있도록 DNS가 그 사이트의 IPv6 주소를 만들어 주고(DNS64), 게이트웨이가 변환합니다(NAT64). 이름으로는 사이트가 열리지만 IPv4 주소를 직접 입력하면 연결되지 않으며, 테스트는 이 점을 알아봅니다. 흔한 구성이고 거의 모든 앱이 잘 동작합니다.

내 데이터를 수집하나요?

아니요. 테스트는 브라우저에서 각 테스트 호스트로 바로 가며, 다른 사이트와 마찬가지로 호스트는 내 주소를 봅니다. 이 사이트는 결과를 받지 않습니다. 공유 링크에는 점수와 테스트 시간만 들어가고 주소는 들어가지 않습니다. 코드는 GitHub에 오픈 소스로 공개되어 있습니다.

IPv4 대 IPv6 비교는 무엇을 보여 주나요?

네 네트워크(Cloudflare, Google, Akamai, DNSPod)에는 각각 IPv4 전용과 IPv6 전용 입구가 있습니다. 테스트는 둘에 동시에 접속하고 열린 연결에서 왕복 시간을 재므로(세 번 중 최솟값), 차이는 서버가 아니라 통신사가 각 프로토콜에 준 경로의 차이입니다. 결론은 두 방식 모두 응답한 네트워크의 차이 중앙값이며, 10 ms(또는 15%) 이내면 같은 속도로 봅니다.

점수에는 영향이 없습니다. IPv6가 조금 느려도 쓸 수 있습니다. Google은 중국 본토에서 응답하지 않고, DNSPod 서버는 중국 본토에 있습니다. 다른 지역에서는 양쪽 모두 느리며, 그 차이는 중국까지의 경로 차이입니다.
